# یوزکیس‌های ادمین کلینیک / بیمارستان (`admin`) — نسخهٔ ۱

در v1 ادمین بیمار را در سیستم و قرارداد ثبت می‌کند، فرم پیش‌پذیرش را مدیریت می‌کند، کلیات را مانیتور می‌کند و کاربران غیر از ادمین کل را مدیریت می‌کند. مدیریت صف اتاق، نوبت زمانی مراجعه و عملیات پذیرش صف‌محور خارج از دامنه است.

### UC-ADM-01 — ایجاد قرارداد سازمانی

- **بازیگر اصلی:** ادمین کلینیک
- **بازیگر ثانویه:** سیستم
- **هدف:** ثبت قرارداد سازمان طرف‌قرارداد
- **پیش‌شرط:** نقش admin
- **پس‌شرط موفقیت:** قرارداد جدید ایجاد شده است
- **اکشن فنی:** `CREATE_CONTRACT`

#### سناریوی اصلی (موفقیت)
1. ادمین قرارداد جدید را باز می‌کند.
2. نام سازمان و مشخصات پایه را وارد می‌کند.
3. سیستم قرارداد را می‌سازد.
4. ادمین به تنظیم ناظر و اعضا ادامه می‌دهد.

---

### UC-ADM-02 — تنظیم ناظر سازمان

- **بازیگر اصلی:** ادمین
- **بازیگر ثانویه:** ناظر سازمان
- **هدف:** تعیین نماینده شرکت برای مانیتور
- **پیش‌شرط:** قرارداد موجود
- **پس‌شرط موفقیت:** ناظر با موبایل فعال روی قرارداد است
- **اکشن فنی:** `UPDATE_CONTRACT_SUPERVISOR`

#### سناریوی اصلی (موفقیت)
1. ادمین نام و موبایل ناظر را ثبت می‌کند.
2. سیستم ناظر را ذخیره می‌کند.
3. ناظر بعداً با OTP وارد پنل مانیتور می‌شود.

### UC-ADM-08 — ثبت بیمار عضو قرارداد در سیستم

- **هدف:** ایجاد پرونده بیمار در سیستم کلینیک از روی عضو قرارداد

2. سیستم پرونده بیمار را می‌سازد و به عضو لینک می‌کند.
3. سلامتجو می‌تواند با موبایل وارد شود و پیش‌پذیرش را پر کند.
4. پزشک بعداً بیمار را در فهرست می‌بیند.

### UC-ADM-18 — خروجی/ورود بسته پرسشنامه

- **بازیگر اصلی:** ادمین (یا ادمین کل / Platform)
- **بازیگر ثانویه:** سیستم
- **هدف:** انتقال کامل تعریف فرم‌ها (بخش، آیتم، مخاطب، visibility) بین محیط‌ها به‌صورت JSON یا Excel
- **پیش‌شرط:** نقش Admin یا Platform؛ کلینیک جاری مشخص
- **پس‌شرط موفقیت:** round-trip بدون از دست رفتن `visibilityRules` و `targetAudience`؛ تعداد فرم‌های واردشده پایدار
- **اکشن فنی:** `GET/POST /api/forms/package` ، `GET/POST /api/forms/package.xlsx`

#### سناریوی اصلی (موفقیت)
1. ادمین در سازنده فرم «خروجی JSON» یا «خروجی Excel» می‌زند.
2. سیستم بستهٔ schemaVersion 2 را برمی‌گرداند / فایل را می‌دهد.
3. ادمین همان بسته را وارد می‌کند.
4. سیستم فرم‌ها را upsert می‌کند و ساختار را هم‌تراز می‌کند.

#### سناریوهای استثنا
- **1x.** فایل خالی یا multipart بدون فایل؛ درخواست رد می‌شود.
- **3x.** JSON نامعتبر یا `TargetAudienceJson` / gender نامعتبر؛ خطا با پیام فارسی.
- **3y.** کد فرم خالی؛ import رد می‌شود.

### UC-ADM-19 — کاتالوگ ماتریس سرطان (seed + مخاطب)

- **بازیگر اصلی:** ادمین
- **بازیگر ثانویه:** سیستم (seed استارت API)
- **هدف:** داشتن دو فرم منتشرشدهٔ ماتریس مرد/زن با شرط نمایش سن و تاهل؛ مشاهده در سازنده از API
- **پیش‌شرط:** استارت API با seed کاتالوگ؛ نقش Admin/Owner/Specialist برای خواندن ساختار
- **پس‌شرط موفقیت:** فرم‌های `cancer_screening_male_v02` و `cancer_screening_female_v02` Published؛ `PREADMIT_V1` آرشیو/غایب از لیست فعال؛ hydrate فرانت از `GET /api/forms/structures`
- **اکشن فنی:** seed `ImportPackageAsync`؛ `GET /api/forms/structures`
- **مرجع ماتریس:** [`docs/شرط-نمایش-و-مخاطب-پرسشنامه.md`](../../شرط-نمایش-و-مخاطب-پرسشنامه.md)

#### سناریوی اصلی (موفقیت)
1. API استارت می‌شود و کاتالوگ CA را idempotent می‌کارد.
2. ادمین سازنده فرم را باز می‌کند و دو فرم سرطان را با مخاطب جنسیت/`ageMin` می‌بیند.
3. ادمین شرط تاهل/سن آیتم‌ها را در UI مشاهده/ویرایش می‌کند (طبق UC-ADM-09).

#### سناریوهای استثنا
- **2x.** نقش بدون دسترسی؛ لیست فرم خالی می‌ماند (403 نادیده در hydrate).

### UC-ADM-16 — ایجاد/ویرایش کاربر

- **بازیگر اصلی:** ادمین کلینیک
- **بازیگر ثانویه:** سیستم
- **هدف:** افزودن یا ویرایش حساب کاربر
- **پیش‌شرط:** نقش admin؛ نقش انتخابی یکی از همه نقش‌ها به‌جز `platform`
- **پس‌شرط موفقیت:** کاربر upsert شده است
- **اکشن فنی:** `POST api/users` / `PLATFORM_UPSERT_USER`

#### سناریوی اصلی (موفقیت)
1. ادمین مشخصات و نقش (Owner / Specialist / Admin / Supervisor در بک‌اند؛ معادل‌های دمو فرانت) را وارد می‌کند.
2. سیستم کاربر را ذخیره می‌کند.
3. در فهرست نقش‌های قابل‌انتصاب، نقش ادمین کل دیده نمی‌شود.

#### سناریوهای استثنا
- **1x.** انتصاب نقش `platform`؛ رد (403).
- **1y.** ویرایش کاربر دارای نقش ادمین کل؛ یافت نشد (404).
