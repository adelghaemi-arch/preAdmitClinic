### UC-PLT-17 — گارد ضدسوءاستفاده API (تکرار بی‌خودی)

- **بازیگر اصلی:** سیستم (تشخیص/تعلیق)؛ ادمین کل (فهرست و بازبینی)
- **بازیگر ثانویه:** کاربر/نشست متخلف؛ ادمین کل دریافت‌کننده SMS
- **هدف:** جلوگیری از تکرار همان/مشابه API که nginx و DB را تحت فشار می‌گذارد؛ فهرست متخلفان برای ادمین کل؛ تعلیق فوری دسترسی؛ اطلاع SMS در صورت فعال بودن پیامک
- **پیش‌شرط:** API در حال سرویس؛ آستانه‌ها از `ApiAbuse__*`
- **پس‌شرط موفقیت:** درخواست‌های burst نرم → `429`؛ سوءاستفادهٔ سخت → `IsActive=false` + revoke نشست‌ها + deny-set حافظه + ردیف `ApiAbuseIncident` + (در صورت SMS زنده) یک پیامک به `09133752696`
- **اکشن فنی:** Early/PostAuth middleware؛ `GET /api/platform/api-abuse`؛ `POST /api/platform/api-abuse/{id}/acknowledge`

#### سناریوی اصلی
1. کاربر غیر Platform همان مسیر را بیش از آستانهٔ soft تکرار می‌کند → `429` + `Retry-After` بدون تعلیق.
2. عبور از آستانهٔ hard → تعلیق حساب، قطع همهٔ نشست‌ها، ثبت حادثه، SMS به ادمین کل (اگر SMS زنده باشد).
3. ادمین کل در پنل پلتفرم فهرست حوادث را می‌بیند و در صورت نیاز acknowledge / فعال‌سازی مجدد می‌کند.

#### سناریوهای استثنا
- **1a.** نقش JWT `Platform` از soft و hard معاف است (قفل‌نشدن ادمین کل).
- **1b.** `Auth__FixedOtp` پر یا SMS پیکربندی‌نشده → تعلیق و فهرست انجام می‌شود؛ SMS نمی‌رود.
- **1c.** شکست ارسال SMS → لاگ؛ تعلیق rollback نمی‌شود.
- **1d.** cooldown یک‌ساعته برای هر user/IP → حداکثر یک SMS و یک حادثهٔ hard فعال.
- **1e.** burst مشروع (مثلاً تا ۴۰ GPS موازی یا confirm ضدتقلب ~۴۸ درخواست) زیر آستانهٔ hard است و تعلیق نمی‌شود.
- **1f.** OTP ناشناس فقط با کلید IP محدود می‌شود (بدون تعلیق User).
- **1x.** state شمارنده تک‌نود (حافظهٔ فرایند)؛ چند replica بدون sticky محدودیت دارد.

### UC-PLT-15 — ورود ادمین کل با OTP

- **بازیگر اصلی:** ادمین کل
- **بازیگر ثانویه:** سیستم
- **هدف:** ورود به پنل پلتفرم با موبایل قفل seed (`09133752696`) بدون قاطی شدن با Patient/Owner
- **پیش‌شرط:** seed Person بدون کدملی + User با نقش `Platform`؛ موبایل در سیستم ثبت
- **پس‌شرط موفقیت:** نشست با نقش `Platform`؛ اگر `Auth__FixedOtp` ست باشد، کد واقعی = پایه + ۱
- **اکشن فنی:** `POST /api/auth/otp/request`، `POST /api/auth/otp/verify`
- **هویت:** حساب staff جدا (`Person.NationalId == null`)؛ حتی اگر Patient روی همان موبایل باشد، فقط کاندیدای Platform

#### سناریوی اصلی (موفقیت)
1. ادمین کل شماره `09133752696` را وارد و درخواست کد می‌دهد.
2. در حالت FixedOtp، UI همان کد پایه (مثلاً `12345`) را نشان می‌دهد و hint «کد ورود = نمایشی + ۱» می‌آید؛ در حالت SMS واقعی hint نمی‌آید و همان کد پیامک وارد می‌شود.
3. ادمین کل **پایه + ۱** را وارد می‌کند (مثلاً `12346`) و وارد پنل ادمین کل می‌شود.

#### سناریوهای استثنا
- **3a.** وارد کردن همان FixedOtp پایه بدون +۱؛ سیستم «کد نامعتبر» می‌دهد.
- **1x.** شماره در سیستم نیست / seed خراب؛ خطا یا نقش غیر Platform.

### UC-PLT-13 — ریست فکتوری کامل

- **بازیگر اصلی:** ادمین کل
- **بازیگر ثانویه:** سیستم (SMS OTP / FixedOtp)
- **هدف:** پاک‌سازی کامل دیتابیس و آپلودها و بازگشت به seed اولیه
- **پیش‌شرط:** نقش platform؛ تأیید OTP روی موبایل کاربر نشست (حتی در Production)
- **پس‌شرط موفقیت:** اسکیما از مایگریشن تجمیعی؛ seed اولیه (از جمله ادمین `09133752696`)؛ پوشهٔ uploads خالی؛ نشست فعلی باطل
- **اکشن فنی:** `PLATFORM_FACTORY_RESET_REQUEST_OTP` / `PLATFORM_FACTORY_RESET_CONFIRM` — `POST api/platform/factory-reset/request-otp` و `…/confirm`

#### سناریوی اصلی (موفقیت)
1. ادمین در تنظیمات پلتفرم «منطقه خطر» را باز می‌کند و درخواست OTP می‌دهد.
2. سیستم OTP با Purpose=`FactoryReset` به موبایل نشست می‌فرستد (یا FixedOtp).
3. ادمین کد را وارد و تأیید نهایی می‌کند.
4. سیستم OTP را مصرف، دیتابیس را Wipe+Migrate، آپلودها را Clear، و seed را اجرا می‌کند.
5. کلاینت logout اجباری می‌شود؛ ورود مجدد با ادمین کل seed ممکن است.

#### استثنا
- کد نامعتبر/منقضی → ریست انجام نمی‌شود.

- **بازیگر اصلی:** ادمین کل (`Platform`)
- **بازیگر ثانویه:** سیستم ذخیره‌سازی (`Storage__Root` → `persist/uploads`)
- **هدف:** مشاهده تامنیل فایل‌های شواهد، بزرگ‌نمایی، و حذف دسته‌ای (مدرک/پرتره/فریم ضدتقلب) با انتخاب همه/هیچ
- **پیش‌شرط:** نقش platform؛ ادمین کلینیک (`Admin`) حتی خواندن ندارد
- **پس‌شرط موفقیت:** حذف منطقی (`DeletedAt`) فایل را از لیست عادی مخفی می‌کند؛ حذف فیزیکی blob + ردیف را پاک می‌کند
- **اکشن فنی:** `GET /api/evidence/vault` · `GET /api/files/{*storageKey}` (پیش‌نمایش) · `POST /api/evidence/vault/soft-delete` · `POST /api/evidence/vault/hard-delete`
- **مسیر دیسک (StorageKey):** `{yyyy}/{NNN}/{guid}_{safeFileName}` — `NNN` سه رقم اول کدملی؛ بدون کدملی → `000`؛ روی هاست زیر `server/persist/uploads`

#### سناریوی اصلی (موفقیت)
1. ادمین کل تب «خزانه فایل» را باز می‌کند (فعال یا سطل زباله).
2. سیستم گرید تامنیل را با هویت بیمار نشان می‌دهد؛ کلیک روی تامنیل فایل را بزرگ می‌کند (lightbox؛ Escape می‌بندد).
3. ادمین همه/هیچ/معکوس را انتخاب و حذف منطقی یا فیزیکی (با confirm) می‌زند.
4. سیستم لیست را به‌روز می‌کند؛ soft فقط `DeletedAt`، hard دیسک+DB.

#### استثنا
- نقش Admin/Owner/Specialist روی endpointهای vault → Forbidden.
- آپلود بدون `patientId` → شارد `000` (سازگاری مسیر قدیمی).
