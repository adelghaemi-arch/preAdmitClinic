# news — ویترین عمومی و اتاق خبر «نفس»

یک سایت چندصفحه‌ای **بدون بیلد** برای سه مخاطب:

| مخاطب | سؤالش | جای پاسخ |
|-------|--------|----------|
| بیمارستان / کلینیک | «این با HIS چه فرقی دارد؟ چقدر وقت و پول می‌برد؟» | `hospitals.html` |
| بیمار / سلامت‌جو | «این سیستم چیست؟ سر من کلاه نمی‌رود؟ داده‌ام کجا می‌رود؟» | `patients.html` |
| شریک / سرمایه‌گذار | «سهم من چطور حساب می‌شود؟ چرا به عدد شما اعتماد کنم؟» | `partners.html` |

صفحه‌ها: `index`، `hospitals`، `patients`، `partners`، `news`، `article`، `voices`، `about`، `contact`.

## اجرا

```bash
cd frontend/news
node serve.mjs          # http://localhost:4321
```

`serve.mjs` سه کار می‌کند:

1. **سرو ایستا** (بدون وابستگی، بدون بیلد).
2. **ری‌لود زنده:** با ذخیرهٔ هر فایل `content/*.json` یا `assets/`، صفحه‌های باز خودکار رفرش می‌شوند. برای فعال شدن، یک بار آدرس را با `?dev=1` باز کنید (یا از دکمهٔ پیش‌نمایش استفاده کنید). حالت dev در همان تب به خاطر سپرده می‌شود.
3. **بازبینی محتوا:** در ترمینال و در آدرس `/__dev/check` می‌گوید کدام فایل JSON شکسته است یا کدام کلید حیاتی جا افتاده — قبل از اینکه صفحه سفید شود.

> فایل‌ها را با دوبار کلیک (`file://`) باز نکنید؛ محتوا با `fetch` خوانده می‌شود.

## تغییر بعدی: کجا را دست بزنم؟

محتوا به **نه فایل موضوعی** تقسیم شده تا هر ویرایش سطح اثر کوچکی داشته باشد:

| فایل | چه چیزی | صفحه‌های اثرپذیر |
|------|---------|------------------|
| `content/site.json` | نام برند، منو (`site.nav`)، تلفن، ایمیل، آدرس، ساعات کاری، نگاشت تصاویر | همه (هدر/فوتر) |
| `content/home.json` | نوار آماری، شش ویژگی، مسیر چهارمرحله‌ای، شش شاهد اعتماد | خانه |
| `content/hospitals.json` | دردهای پذیرش، سه مدل استقرار، نقش‌ها و دسترسی، چهار هفتهٔ استقرار، سه پلن | بیمارستان و کلینیک |
| `content/partners.json` | سه مدل مشارکت، قواعد دیوار شیشه‌ای | مشارکت |
| `content/news.json` | خبرها (فهرست، فیلتر، جست‌وجو، صفحهٔ مقاله) | اتاق خبر، مقاله، خانه |
| `content/voices.json` | روایت‌ها و برچسب نقش (`tag` = فیلتر صفحه) | روایت‌ها |
| `content/faq.json` | چهار دسته: `general`، `hospital`، `patient`، `partner` | تماس، بیماران، مشارکت |
| `content/about.json` | چهار اصل، نقشهٔ راه، تیم | درباره |
| `content/contact.json` | موضوع‌های فرم تماس | تماس |
| `content/intake.json` | **ساختار پروندهٔ پیش‌پذیرش** — فرم‌ها، بخش‌ها، تعداد سوال و پکیج‌های چکاپ (ساختهٔ `tools/build-intake.mjs`) | خانه، بیمارستان، بیماران |

### ساختار پروندهٔ پیش‌پذیرش — `intake.js` + `content/intake.json`

بلوک «پروندهٔ پیش‌پذیرش، دقیقاً مثل فرم اصلی» در **خانه، بیمارستان و کلینیک، و برای بیماران** نمایش داده می‌شود.
عددهایش دستی نوشته نشده‌اند؛ از کاتالوگ واقعی فرم ساخته می‌شوند:

```bash
node tools/build-intake.mjs     # از form-catalog.seed.json → content/intake.json
```

| منبع | چه چیزی می‌دهد |
|------|----------------|
| `frontend/my/src/lib/form-catalog.seed.json` | عنوان بخش‌ها، متن سوال‌ها، `visibilityRules`، `inputType`، `required` |
| `backend/src/Nabz.Application/Identity/CorporatePathwayStationCatalog.cs` | چهار مسیر چکاپ سازمانی و ترتیب ایستگاه‌ها |

**قاعدهٔ مهم:** عدد «تعداد سوال» برای هر پکیج با فیلتر کردن سوال‌های نامرتبط حساب می‌شود.
مثلاً غربالگری پروستات و رودهٔ بزرگ شرط `age >= 50` دارند، پس در «چکاپ آقایان ۴۰+» (بازهٔ ۴۰ تا ۴۹)
دیده نمی‌شوند. اگر برای یک بیمار هیچ سوالی در بخشی نماند، آن بخش از استپر حذف می‌شود — همان قاعدهٔ `form-engine.ts`.

`node check.mjs` این بلوک را با کاتالوگ مقایسه می‌کند: اگر تعداد سوال یا بخش با `form-catalog.seed.json`
نخواند، **خطا** می‌دهد. پس عدد بی‌پشتوانه منتشر نمی‌شود.

**افزودن پکیج چکاپ جدید:** یک شیء در آرایهٔ `pathways` داخل `tools/build-intake.mjs` اضافه کنید
(کد، عنوان، جنسیت، بازهٔ سنی، فرم مرتبط، ایستگاه‌ها) و بعد `node tools/build-intake.mjs` را اجرا کنید.

**افزودن خبر:** یک شیء در `content/news.json` اضافه کنید؛ فهرست، فیلتر (`category`)، جست‌وجو و `article.html?id=…` خودکار به‌روز می‌شوند. `id` باید یکتا باشد و `image` یکی از `reception` / `doctor` / `patient`.

**افزودن صفحهٔ تازه:** پوستهٔ HTML را از یکی از فایل‌ها کپی کنید (فقط `title` را عوض کنید)، سپس در `app.js` یک رندرر بنویسید و در `PAGE_RENDERERS` ثبت کنید. یک ردیف هم در `site.nav` بگذارید. `node check.mjs` می‌گوید چیزی جا افتاده یا نه.

## ابزارها

| دستور | کار |
|-------|-----|
| `node serve.mjs` | پیش‌نمایش + ری‌لود زنده + بازبینی مداوم |
| `node check.mjs` | بازبینی کامل پیش از کامیت (JSON، کلیدهای حیاتی، شناسهٔ تکراری، تصاویر، پوسته‌ها، ارقام فارسی) — خروجی خطا با کد ۱ |
| `curl localhost:4321/__dev/check` | همان بازبینی به‌صورت JSON |

`check.mjs` را قبل از هر کامیت اجرا کنید؛ اگر خودکارتر می‌خواهید، در `.git/hooks/pre-commit` صدایش بزنید:

```bash
printf '#!/bin/sh\nnode frontend/news/check.mjs || exit 1\n' > .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```

## ساختار فنی

```
frontend/news/
├── index.html … contact.html   # ۹ پوستهٔ سبک؛ محتوا با JS رندر می‌شود
├── app.js                      # رندر صفحه‌ها + آیکون‌های SVG + تعامل‌ها
├── content/                    # ۱۰ فایل محتوای موضوعی (منبع یگانهٔ متن)
├── intake.js                   # بلوک ساختار پرونده (پکیج‌های چکاپ + استپر بخش‌ها)
├── tools/build-intake.mjs      # ساخت content/intake.json از کاتالوگ واقعی فرم
├── styles.css                  # توکن‌ها، کامپوننت‌ها، RTL و ریسپانسیو
├── serve.mjs                   # سرور پیش‌نمایش/توسعه بدون وابستگی
├── check.mjs                   # بازبینی محتوا پیش از کامیت
└── assets/
    ├── fonts/                  # Vazirmatn (بدنه) + Lalezar (تیتر برند) — محلی، بدون CDN
    ├── img/                    # سه تصویر ادیتوریال نمونه
    └── favicon.svg
```

- **بدون وابستگی و بدون بیلد:** بازکردن پوشه روی هر هاست ایستا کافی است (همان الگوی `server/news`).
- **بارگذاری موازی:** فایل‌های محتوا هم‌زمان خوانده و ادغام می‌شوند؛ حالت شکست هر فایل جداگانه گزارش می‌شود.
- **فونت محلی:** پیش‌نمایش بدون اینترنت هم درست دیده می‌شود.
- **تعامل‌ها:** سوییچ مخاطب در هیرو، فیلتر و جست‌وجوی خبر، فیلتر روایت‌ها، تب‌های پرسش متداول، فرم‌های نمونه، ماشین‌حساب سهم شریک.
- **فرم‌ها فعلاً فقط نمایشی‌اند** (`data-form`) و چیزی ارسال نمی‌کنند؛ برای اتصال، در `initForms` نقطهٔ ارسال اضافه کنید.

## قواعد محتوایی (مهم)

1. **هر عددی که ادعاست، برچسب «نمونه» دارد.** اعداد پایلوت تا وقتی داده واقعی نداریم، نباید به‌عنوان نتیجه منتشر شوند.
2. **روایت‌ها نمونه‌اند** و در صفحه هم صریح نوشته شده؛ با گرفتن رضایت کتبی، متن و نام واقعی جایگزین شود.
3. **هیچ‌جا نمی‌گوییم جایگزین HIS یا پروندهٔ رسمی هستیم.** این مرز، هم در متن و هم در صفحهٔ بیماران حفظ شده.
4. **حریم خصوصی بیمار با زبان ساده** نوشته شده (چه چیزی، چرا، چه کسی می‌بیند) — همان جدول در صفحهٔ `patients` و در سند [پرسشنامه](../../docs/شرط-نمایش-و-مخاطب-پرسشنامه.md) باید هم‌خوان بماند.
5. مسیر و لحن «دیوار شیشه‌ای» نباید به وعدهٔ حقوقی تبدیل شود؛ تعهد عددی فقط در توافق‌نامه.

## طرح‌های پیشنهادی (پوشهٔ جدا)

چهار طرح جایگزین برای همین محتوا در [`designs/`](designs) گذاشته شده‌اند تا مقایسه شوند — هرکدام یک صفحهٔ کامل و مستقل:

```bash
node serve.mjs          # → http://localhost:4321/designs/
```

۰۱ «میز خبر» (روزنامه‌ای) · ۰۲ «شاهد» (داشبورد روشن) · ۰۳ «مجلهٔ بالینی» (تصویرمحور) · ۰۴ «شب دیجیتال» (فنی/تیره).

این پوشه روی سایت مستقر (همین ریشه) اثری ندارد و در ناوبری نیامده است. مقایسه، معیار انتخاب و مسیر تبدیل در [`designs/README.md`](designs/README.md) آمده است.

## مرحلهٔ بعد (اگر طرح تأیید شد)

- دیپلوی همان ساختار ایستا روی `server/news` ([راهنما](../../docs/shared/server-deploy.md)) — بدون تغییر محتوا.
- اتصال فرم دمو به یک endpoint واقعی (`POST /news/lead`) و ثبت در `persist/news-data`.
- اگر تعداد خبرها زیاد شد (بیش از ~۳۰)، تولید `content/news.json` از Markdown یا یک CMS سبک.
- بازبینی حقوقی متن‌های حریم خصوصی و شرایط پایلوت پیش از انتشار عمومی.
